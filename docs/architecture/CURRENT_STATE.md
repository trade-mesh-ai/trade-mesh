## Design Review Findings (2026-07-15) — All 10 Resolved, Verified, and Committed

**Context:** Principal Engineer design-coherence review conducted across 5 sections (capital & risk architecture, strategy selection & market-regime logic, paper-to-live transition, failure-mode design, data & state model), per Kuldeep's request for a structured top-to-bottom review of TradeMesh's design before live trading work begins. Conducted against real pasted evidence (source files, grep output, migrations, Liquibase execution logs) — not narrative. This review **superseded and rejected** two Cline-generated documents (`Architecture.md`, `ArchitectureReview.md`) as unreliable review input: the review document contained a fabricated "no unit tests found in codebase" claim (357 tests actually passed on `main` at review start), scored the system 8.2/10 "production-ready" partly on that basis, and gave zero dedicated treatment to the paper-to-live transition despite that being the stated purpose of the exercise. Both documents also independently described `OrderExecutionService` as an active, functioning component; it is confirmed dead code with zero callers.

**Cross-section synthesis (unchanged from original review):** The findings below share one root pattern, found independently in each section — a real, working mechanism exists alongside a second thing that looks like it does the same job but is dead, broken, or was never wired in, and documentation asserted the non-functional one as real. Confirmed a second time during implementation: `RiskManager`'s dead risk-check surface, `StrategySelector`'s dead priority switch, `OrderExecutionService`'s obsolete signal model, and the duplicate token-health monitors all fit this same pattern. This is not carelessness; it's the natural residue of fast, evidence-disciplined feature development without a periodic whole-system coherence pass.

**Process note worth recording:** every finding below went through the same discipline used throughout this project — Cline proposed a plan, the plan was reviewed and frequently challenged before approval (three findings, #5/#9/#7, were substantially revised or reversed after direct challenge before implementation), implementation was verified against real command output pasted by Kuldeep, not accepted on Cline's self-report. ## OptionChainService Live-Fallback Refactor (2026-07-20) — Closing the Actual Root Cause Behind Friday's P&L-Corruption Incident

**Context:** Originally scoped as "Option B" — defer a STOP_LOSS/TARGET_HIT close by one cycle if the underlying price data was known to be a fallback, rather than commit to a hardcoded-zero or stale value (the fallback fix already shipped on 2026-07-17). Before implementing Option B, a direct question reframed the whole approach: **why defer or use stale data at all, when a live Kite fetch could be attempted instead?**

**Investigation found the real fix already existed and just needed wiring in.** `OptionChainService.fetchOptionChain(String symbol)` was confirmed to already implement cache-first-with-live-Kite-fallback: try Redis, and on a genuine cache miss, fetch fresh from Kite directly, then re-cache the result with the same key/TTL convention `PaperTradingEngine` reads from. This method already has 8 other real callers across the codebase (`MarketIntelligenceService`, `IvHistoryService`, `MarketMetricsService`, several schedulers/controllers) — well-exercised, trusted infrastructure. **`PaperTradingEngine` never called it** — it bypassed this entirely, reading Redis raw and falling back to a stale value on *any* cache miss, never attempting a live fetch. This was the actual root cause underlying 2026-07-17's `realizedPnl: 0.00` incident, not merely a symptom the earlier fallback fix (Option A) had softened.

**Confirmed no circular dependency risk** before proceeding: the `zerodha.options` package never imports `execution`, and `PaperTradingEngine` already imports `OptionChain` (the data type) from that same package — the dependency direction was already safely one-way.

**Fix:** added `OptionChainService` as a 9th constructor field on `PaperTradingEngine` (appended after the existing 8, preserving positional-argument compatibility). Refactored `calculateIronCondorPnl()`, `calculateSpreadPnl()`, and `fetchCurrentPrices()` to call `optionChainService.fetchOptionChain()` instead of reading Redis directly — per-leg netting loops left byte-for-byte unchanged, only the data-fetching mechanism changed. Each method's existing fallback value is preserved exactly, now triggered only on a genuine `fetchOptionChain()` failure (no token, Kite itself down) rather than any simple cache miss. The two fully-dead `LOT_SIZES.getOrDefault()` lines inside the two P&L methods (confirmed dead earlier the same day) were naturally removed as part of this change, since the block they lived in was replaced.

**Required updating all 8 test files that manually construct `PaperTradingEngine`**, and two real correction rounds, both caught via actual test-failure evidence rather than accepted on a plan summary:
1. `PaperTradingEngineMarkToMarketDecisionTest`'s constructor was initially given `null` for the new dependency, on the reasoning that it "doesn't call the refactored methods" — **wrong**: this file directly tests `markToMarket()`'s default branch, which calls `fetchCurrentPrices()`. Confirmed via a real failing trade returned completely unmutated (fallback silently firing when it shouldn't have). Fixed with a real mock and proper stubs.
2. `PaperTradingEngineCurrentValueTest`'s two pre-existing "successful path" tests (from the earlier Redis-fallback test group) were never updated to stub the new dependency for a success case, confirmed via a real failure (`predicate failed on value: 0.0`, consistent with an unstubbed mock throwing and silently falling back). **Explicitly reconsidered afterward, at Kuldeep's prompt, whether this was truly the best solution — a real, useful design discipline worth recording:** raised whether the lack of single-flight de-duplication (multiple concurrent positions on the same symbol each independently calling Kite on a simultaneous cache miss, e.g. right after a restart) posed a real risk given Kite's API rate limits. On reconsideration, concluded this would be overengineering to address specifically here: the concurrent-position cap bounds this to at most 3 simultaneous calls (not unbounded), this is paper trading (no real-capital consequence if a quote call is briefly rate-limited), and — the key point — this exact risk already exists, unaddressed, across all 8 of `fetchOptionChain()`'s other existing callers; building bespoke protection inside `PaperTradingEngine` alone would solve the same problem in the wrong place. If ever warranted, single-flight de-duplication belongs once, inside `OptionChainService` itself, for all 9 callers' benefit — logged as a possible future system-wide item, not urgent, no demonstrated incident.

**One genuinely new, separate observation surfaced during that reconsideration, worth tracking:** the option-chain cache's TTL (3 minutes) is shorter than `OptionChainSnapshotScheduler`'s refresh interval (5 minutes) — meaning there's a routine ~2-minute window every cycle where the cache is *expected* to be empty before the next scheduled refresh. A cache miss during this window is arguably a normal, regular occurrence, not a rare restart-only edge case. This doesn't change today's fix (the same observation applies whether or not `PaperTradingEngine` calls `fetchOptionChain()`), but is worth a future look at whether the TTL/refresh-interval mismatch was ever a deliberate choice.

## `calculateAdjustedExitLevels()` — Design Review, Decision Deferred (2026-07-21)

**Context:** Investigating the 2026-07-10 "dead/disconnected feature" note as part of today's cleanup pass. Re-verification found the original framing imprecise: `calculateAdjustedExitLevels()` computes real ATR-based adjusted profit-target/stop-loss levels, attaches them to `IronCondorSignal` (`adjustedProfitTarget`/`adjustedStopLoss`), and writes them into entry metadata — confirmed via direct grep that `PaperTradingEngine.shouldExitIronCondor()` never reads either field; the real exit gate uses flat `cfg.getStopLossPercent()`/`cfg.getTargetProfitPercent()` only. This is a live documentation/behavior mismatch, not harmless dead code: metadata visible in alerts/API responses implies volatility-adjusted exits are active for a given trade when they never have been for any Iron Condor trade to date.

**Explicit decision, made deliberately rather than inferred:** fixed-percentage exits remain the correct V1 baseline. Reasoning — Iron Condor has exactly one real live trade to its name (2026-07-16/17, and even that trade's `realizedPnl` is separately confirmed unreliable, see Live Monitoring Findings above), meaning there is zero empirical evidence to justify any dynamic exit adjustment. Changing exit philosophy now would be optimizing against no data, which is worse than doing nothing.

**Design questions (answerable now, from first principles) resolved separately from calibration questions (require live data, not resolved):**
- IV/HV ratio is the theoretically better volatility input than ATR% for a premium-selling strategy — ATR is backward-looking realized price range, an indirect proxy; IV/HV directly reflects whether collected premium was rich or cheap relative to what actually happened.
- Target and stop-loss should NOT be adjusted symmetrically with volatility. Widening the stop-loss in high-volatility conditions (as the current unwired implementation would do) increases tail-risk exposure exactly when a position is most likely to actually breach — the opposite of what a stop-loss is for.
- These two conclusions are banked for whenever dynamic exits are properly designed, backtested, and evaluated as their own future strategy enhancement — not implemented as a side effect of resolving today's ambiguity.

**Decision on the orphaned code itself: deliberately left open, not resolved.** Two options remain, both undecided: (a) delete `calculateAdjustedExitLevels()` and the two metadata fields entirely if dynamic exits are ultimately not pursued, or (b) wire it in properly as a real, calibrated, backtested feature once the design questions above are actually acted on. **This ambiguity should not be left indefinitely** — flagged explicitly so it isn't silently re-discovered as a "mystery" a third time in a future session.

No code changed. This was a design-review-only session item.

## Locked Three-Gate Risk Architecture Redesign (2026-07-26) — Not Yet Implemented

**This is the main output of the 2026-07-26 session.** A full, from-scratch redesign of the three-gate risk architecture (entry / position sizing / exit) was designed, reviewed against four external AI critiques (ChatGPT, Grok, Perplexity, Gemini), and locked. Nothing has been implemented yet — this section is the design specification for a phased implementation, starting with `feature/trade-risk-snapshot-phase1`.

### Why this was undertaken

Investigating whether `calculateAdjustedExitLevels()` (the orphaned ATR-based exit-adjustment code, logged 2026-07-10, reviewed 2026-07-21) should be wired in or deleted led to a direct challenge: **its stop-loss logic widens when volatility rises — the opposite of standard risk practice** (rising volatility should mean reduce risk — smaller size, tighter stops, earlier hedging — not "allow bigger losses"). This is not a calibration question that more data would resolve; the underlying logic is backwards. **Verdict: `calculateAdjustedExitLevels()` will NOT be wired in as-is. Recommended action: delete the dead code — the redesign below supersedes it properly. Not yet deleted.**

This prompted a full redesign of all three gates together, done properly rather than patching the old code.

### The locked architecture

**Layer 0 — Market Regime** *(already exists today, no code change — just formally named as its own layer for clarity)*
VIX range checks, allowed-days, latest-entry-time, no-duplicate-open-position-for-same-strategy. These already run before confidence scoring in the current codebase.

**Layer 1 — Entry Quality**
- Confidence score = **IV/HV + PCR + trend strength only.**
- **ATR% bands REMOVED from the confidence score** — currently present at `BearCallSpreadStrategy.java` lines 91-95 (`atrPct < 0.36 → +15`, `< 0.48 → +20`, `< 0.60 → +10`) and the equivalent in `BullPutSpreadStrategy.java`. Removed because ATR gets its own dedicated job in Layer 2 below (see "core principle"), and leaving it in scoring would mean the same physical fact (today's volatility) silently influences two supposedly-independent gates — the exact "sizing-vs-scoring double-count" failure mode this project already caught and fixed once with VIX (2026-07-09 ADR).
- **New hard veto:** `atrPercentile > 90` → skip entry entirely, regardless of confidence score. A rare, deliberately conservative circuit breaker — not a soft filter (confidence/sizing already handle normal-to-moderate volatility variation).
- If `atrPercentile == null` (insufficient history — see below) → treat as neutral (50), do NOT veto.

**Layer 2 — Risk Engine**
```
atrMultiplier      = 0.85 + (atrPercentile / 100) × 0.50      → range 0.85–1.35
stopDistancePoints = baseStopLossPercent × entryCredit × atrMultiplier
plannedRiskPerLot  = stopDistancePoints × lotSize
lots = capital ÷ plannedRiskPerLot → VIX scale (unchanged) → confidence scale (unchanged) → maxLots cap (unchanged)
```
- VIX-scaling and confidence-scaling stay **exactly as they are today** — this redesign does not touch either.
- **Key mechanism, not a new sizing stage:** since sizing is already `capital ÷ riskPerLot`, a wider ATR-adjusted stop distance automatically shrinks lot count through that existing division — no new multiplier stage bolted on, no new interaction risk with the existing VIX/confidence multipliers. Total rupee risk on the trade stays pinned to the fixed risk budget (`capital × riskPercentPerTrade`) regardless of ATR — this is what makes the design safe rather than risk-increasing, verified by walking the arithmetic through explicitly (Grok's objection that "ATR-adjusted stop distance increases risk per lot" is true per-lot but doesn't account for lots shrinking correspondingly — **rejected**, see below).
- **Naming: `plannedRiskPerLot` is a NEW, distinct concept — do not rename or conflate with the existing `maxLossPerLot`**, which keeps its current meaning (worst-case wing-width-based loss, used for reporting/margin/exposure analytics) and is used unchanged elsewhere (e.g. the aggregate risk-dollar cap from earlier this week).

**Layer 3 — Execution**
Strike selection — unchanged.

**Layer 4 — Exit**
```
targetMultiplier = 0.90 + (atrPercentile / 100) × 0.45        → range 0.90–1.35
targetThreshold  = baseTargetProfitPercent × entryCredit × lots × targetMultiplier
```
- Stop-loss uses the **exact same `stopDistancePoints`** value computed in Layer 2 — single source of truth, no separate recomputation (this directly closes the class of bug fixed 2026-07-24, where `shouldExitSpread()` recomputed its own, different, wrong `maxLoss` instead of reusing the entry-time value).
- **Both `stopDistancePoints` and `targetThreshold` are frozen at entry time and persisted — NEVER recalculated during the trade's life**, even though live ATR/VIX continue to change every 60-second mark-to-market cycle. This applies equally to target, not just stop-loss — a design question that was explicitly raised and answered (see "Freezing target, not just stop-loss" below).
- VIX-panic, DTE-exit, leg-breach checks — all unchanged, still run before SL/target in the existing priority order.
- If `atrPercentile == null` → multiplier = 1.0 (exactly today's unadjusted behavior).

**Core principle:** one ATR reading, computed once at entry, does exactly two jobs — sizes the position and sets the stop distance — and is never recomputed or double-counted anywhere else in the pipeline.

### Key discovery that changed the design mid-session

`atrPercentile` **already exists** — confirmed via direct code read: `MarketMetrics.java:55` (real field), computed in `MarketMetricsService.calculateATRPercentile()` (line 316), using a 74-day rolling window, smoothed-current-ATR14-vs-smoothed-historical-distribution, returns 0–100, returns `null` on insufficient history (fewer than 15 of the last 74 days available).

The design originally specified building a new `atrRatio = currentAtr ÷ 20-day-baseline-average`. **This was abandoned once `atrPercentile` was found**, because: it requires zero new indicator code (already computed on every metrics cycle), it's naturally bounded 0–100 with no clamping needed on the raw input, it's outlier-resistant by construction (a percentile barely moves from one abnormal day, whereas a mean-based ratio can be badly distorted by a single outlier), and its 74-day window independently addresses a concern one reviewer raised about a short baseline "catching up" too fast during a prolonged volatile regime.

**Incidental finding while reading this code, not yet actioned:** `MarketMetricsService.java` line 341 has a stray `System.out.println("DEBUG: full distribution = " + atrDistribution)` running in production on every metrics calculation. Should be removed or downgraded to `log.debug`. Low priority, unrelated to this redesign, logged so it isn't lost.

### Why persist a full `TradeRiskSnapshot`, not just the derived stop/target values

This exact question was asked directly and reasoned through explicitly, rather than left implicit — recorded here in full since the reasoning, not just the resulting field list, matters for whoever implements or later touches this.

**The decisive argument is config drift, not market-data reconstruction.** Market data (ATR, VIX, etc.) is at least partially reconstructable later from `NiftyDailyPrice` history. What is never reconstructable is config state: if `stopLossPercent`, `minScore`, or any other config value is ever tuned in `application.yml` next month, every historical trade that used the old value becomes silently unexplainable — a future analyst recomputing "what should this trade's threshold have been" with *today's* config would get a different, wrong answer and could mistake correct historical behavior for a bug. This project has already been burned by a milder version of exactly this pattern (`maxLoss: null` on every trade predating the 2026-07-22 aggregate-risk-cap feature).

**Checked field by field, what's actually unrecoverable without a snapshot:**
- Daily/baseline ATR — mostly reconstructable from `NiftyDailyPrice` history
- Intraday VIX at the fill moment — **not recoverable**, only the current cached value exists
- PCR, IV/HV, IVR at the fill moment — **not recoverable**, option-chain snapshots expire from Redis
- Confidence score — currently only in signal metadata as an unqueryable string
- Config values as of entry (`stopLossPercent`, `minScore`, etc.) — **never recoverable**, YAML has no version history

Three of five are permanently lost without a snapshot — this settled the decision.

**Storage shape, decided:** real, individually-typed columns (`BigDecimal`/`Integer`) for values that participate in decisions or will definitely be queried/filtered on in future analysis (`stopDistancePoints`, `targetThreshold`, `plannedRiskPerLot`, `atrPercentile`, `confidenceScore`). Everything wider (current VIX, PCR, IV/HV, IVR, the effective config values actually used) goes into one `riskSnapshot` JSONB column — avoids a schema migration every time one more piece of entry-time context is worth capturing, matching the existing precedent of the `legs` JSONB column.

**Explicit scope boundary, to prevent open-ended scope creep:** snapshot only the inputs that actually fed an entry-time decision — not "every market metric available."

**The one real risk with this design, to guard against explicitly:** a snapshot exists for explanation and analysis, never for live decision-making. If any future code reads a snapshot field other than the two frozen decision values (`stopDistancePoints`, `targetThreshold`) inside a live check, that is a stale-data bug — and a subtle one, since the value will look legitimate. A new `.clinerules` rule is planned (not yet written) to make this explicit: *snapshot fields are read-only for reporting/analysis; the only snapshot values permitted in live decision logic are `stopDistancePoints` and `targetThreshold`.*

### Freezing target, not just stop-loss — explicitly reasoned, not assumed

Whether `targetThreshold` should also freeze at entry (versus recomputing live, since — unlike stop-loss — it has no arithmetic coupling to position sizing) was raised directly and decided independently, not by deferring to any of the four external reviews. Two project-specific reasons, both explicit:
1. **Analyzability.** With near-zero real trade history, a frozen number gives a clean before/after comparison once real data accumulates; a target that drifted continuously through a trade's life gives nothing analyzable.
2. **Consistency, given this project's own history of bugs.** "Stop freezes, target doesn't" would create exactly the kind of two-similar-things-behave-differently trap that has caused real, confirmed bugs here repeatedly (per-lot vs. aggregate confusion, points vs. rupees confusion). One rule applied uniformly removes an entire class of future confusion.

If real trade data later shows frozen targets systematically underperforming in volatile regimes, revisiting target-only recomputation is a legitimate future change — with evidence behind it, the same evidentiary bar this project applies to every other tuning decision.

### External AI review — what was adopted, what was rejected, and why

Four external tools (ChatGPT, Grok, Perplexity, Gemini) reviewed an earlier draft of this design. Their input was weighed on technical merit, not deferred to as authority — explicitly confirmed with the user that the final call is this project's own.

**Adopted:**
- Rename the sizing-input concept `plannedRiskPerLot`, distinct from the existing `maxLossPerLot` (ChatGPT) — prevents exactly the kind of naming collision/reused-meaning bug this project has hit before.
- Add an explicit entry-time ATR extreme-outlier veto, separate from removing ATR from the confidence score (Gemini/Grok both raised versions of this) — accepted as a real gap in the original proposal.
- Keep the target-side ATR clamp tighter/more conservative than the stop-side clamp (multiple reviews converged on this independently) — adopted (`0.90–1.35` vs. `0.85–1.35`).
- Persist `stopDistancePoints`/`targetThreshold` at fill time, never recompute mid-trade (Gemini) — adopted, and extended to include the full snapshot reasoning above.

**Rejected, with reasoning — do not silently revisit:**
- **Grok's alternative:** use ATR to set strike/wing-width distance instead of stop distance, keep stop-loss as a fixed multiple of credit. Rejected because the objection it was solving — "a wider ATR-adjusted stop increases rupee risk" — doesn't actually hold once the sizing division is walked through explicitly: `capital ÷ riskPerLot` keeps *total* risk pinned to the fixed budget even as *per-lot* risk grows via a wider stop. Grok's alternative is a legitimate idea for a separate, larger redesign of trade construction itself, but it is not a fix for a problem that exists in the adopted design.
- **ChatGPT's "verify original designer intent before removing ATR from confidence."** Rejected as a framing, not as a caution — there is no traceable, recoverable "original intent" in this codebase's iterative, multi-session history to verify. The decision stands on current, direct reasoning (double-count avoidance, argued and confirmed with real code showing ATR% already present in the confidence formula), not on archaeology of past intent.
- **ChatGPT's suggestion to use a z-score instead of a raw ratio** for outlier resistance. Rendered moot — the already-existing `atrPercentile` provides the same outlier resistance for free, with zero new code.
- **Gemini's suggestion of a 50-day baseline instead of 20-day.** Also rendered moot once `atrPercentile` (74-day window) was adopted in place of building a new ratio at all.
- **Gemini's "VIX+ATR double-dip" concern** (both signals correlate, so a compound-stress day could shrink sizing twice). Acknowledged as real, but accepted rather than engineered around: in a genuine compound-stress scenario, total risk ends up *below* the intended budget, not above it — a capital-efficiency cost (potentially over-cautious sizing on a bad-but-still-tradeable day), not a safety defect. Flagged to monitor once live; not a blocker for this design.

## Critical Fix — Spread Stop-Loss Units Mismatch (2026-07-24)

**This is the most significant finding of the session, and arguably of the entire project so far.** Found entirely by accident, while building a display feature (stop-loss/target thresholds for `GET /trading/positions/open`) — not by any dedicated testing or code review effort.

**The bug:** `shouldExitSpread()`'s stop-loss check (Check 3) computed its threshold in **RUPEES** (`wingWidth × lotSize × lots`, ~₹45,500 for a real 7-lot trade), but compared it directly against `unrealizedPnl`, which is in **POINTS** (confirmed: `calculateSpreadPnl()` only multiplies by `leg.getQuantity()`, never by lot size — this has been the documented, enforced P&L-in-points convention throughout this project since day one). A defined-risk credit spread's maximum possible points-loss is structurally bounded by wing width (~78 points for a 100-point wing here) — nowhere close to a rupee-scale number in the tens of thousands. **This meant the stop-loss safety net for `BULL_PUT_SPREAD` and `BEAR_CALL_SPREAD` has been non-functional since this code was written** — mathematically unreachable by any realistic market movement.

**How it was found:** while implementing the display feature, the first draft (using `trade.getMaxLoss()`, rupees) produced an absurd `stopLossThresholdAmount` of `-2,300,935` for a real 7-lot trade — off by roughly 65×. Rather than accept a plausible-sounding "unit-agnostic comparison" rationalization, the investigation was pushed further: real production trade history was queried directly, confirming **zero `STOP_LOSS` exits exist for any spread trade after 2026-07-20** (the multi-lot scaling fix date) — fully consistent with the threshold being unreachable. The existing unit test (`spread_7lots_stopLoss_atScaledThreshold`, added 2026-07-20) had not caught this because it passed a hand-constructed `unrealizedPnl` value (`-45500.0`) chosen to exactly match the buggy threshold, rather than a realistic points-based P&L a real spread could ever reach — it validated internal arithmetic self-consistency, not real-world reachability.

**The fix:** replaced the wing-width/`maxLoss`-based (rupee) threshold with the same `entryCredit`-based (points) formula already used correctly by `shouldExitIronCondor()`'s stop-loss and by `shouldExitSpread()`'s own profit-target check (Check 4, in the same method) — `stopLossThreshold = -(entryCredit × lots × stopLossPercent / 100)`. This makes all three of Iron Condor's stop-loss, Iron Condor's target, and both spreads' stop-loss and target structurally identical in shape, removing `wingWidth`/`LOT_SIZES`/`maxLoss` from this method entirely. A design question (should spread stop-loss be based on % of credit or % of max theoretical wing-width loss?) was considered and resolved in favor of matching the already-correct, already-tested pattern — the lower-risk choice, and consistent with how the config value is named (`stopLossPercent`, implying % of something already known — credit — not a separate risk-model concept).

**Test suite fallout, traced and fixed completely:** correcting the existing test's expected value (`-45500.0` → `-70.0`, matching the new formula on that test's own fixture data) caused 9 `UnnecessaryStubbingException` failures to surface, in 4 different test files (`PaperTradingEngineMultiLotExitTest`, `PaperTradingEngineDteExitTest`, `PaperTradingEngineLegsBreachTest`, `PaperTradingEngineVixPanicTest`) — because removing the now-unused `wing-width` config lookup from production code made a shared config stub genuinely unused across several unrelated test methods. Traced methodically: confirmed via `git stash`/re-run that these 4 files passed cleanly *without* the fix and failed *with* it, proving direct causation rather than pre-existing flakiness; then removed all now-unnecessary `wing-width` stubs across all 4 files (took two passes — the first attempt missed several occurrences in files with multiple test methods). Added 2 new tests using realistic points-based P&L values (`-75.0` triggers, `-65.0` does not) specifically to make explicit, in the test suite itself, that the fix changes real-world behavior, not just internal arithmetic.

**Verification:** real diff reviewed for every one of the 5 changed files, `compileJava` clean, full `clean build`, **378/378 tests passing** (376 baseline + 2 new), and live-confirmed twice against the real running app and a real open trade — `stopLossThreshold` correctly showing `-155.4` points for a real 7-lot Bear Call Spread (`22.2 × 7 × 100%`), matching hand calculation exactly, a world away from the `-35,399`/`-2,300,935` nonsense seen before the fix.

**Stage 4c override:** explicitly invoked — this touches `shouldExitSpread()` directly, live exit-decision code, with real safety implications (a non-functional stop-loss). Given the severity, this was prioritized ahead of the display feature that surfaced it, and merged same day.

**Commit:** `37a7067` on `fix/spread-stoploss-units-mismatch`, merged to `main` via `cb4fd7f`.

**Separate, still-open anomaly noted during this investigation, not yet resolved:** the real open 7-lot Bear Call Spread trade showed `unrealizedPnl: -127.75` at one point, which appeared to exceed the theoretical maximum points-loss for a 100-point-wide credit spread (~77.8 points, bounded by wing width). This was set aside to prioritize the units-mismatch fix and has not been independently re-investigated — flagged below as a tracked gap. The position's `unrealizedPnl` has since moved (to `-98.7`, then `-134.4`) as real market conditions changed, which is expected and does not by itself resolve or dismiss the original anomaly.

## Portfolio-Level Aggregate Risk-Dollar Cap (2026-07-22)

**Context:** Direct follow-through on the two gaps logged earlier the same day (see "Position Sizing — Institutional Comparison" below). ## Multi-Lot `currentValue` Scaling Bug (2026-07-22) — Found Live, Fixed Same Day

**Context:** While investigating the Telegram alert Max-Profit gap on the same live 7-lot Bear Call Spread trade, a direct look at the trade's full JSON (`GET /paper/trades/{id}`) surfaced a second, unrelated, more serious issue: `currentValue: -2.95`, a figure with no sensible interpretation for an open credit spread showing a positive `unrealizedPnl`.

**Root cause, confirmed via code, not inference:** `markToMarketIronCondor()` and `markToMarketSpread()` both computed `trade.setCurrentValue(trade.getEntryCredit().subtract(pnl))` — but `trade.getEntryCredit()` is the raw, unscaled per-single-lot value, while `pnl` (from `calculateIronCondorPnl()`/`calculateSpreadPnl()`) is already scaled by `leg.getQuantity()`. Subtracting an unscaled per-lot figure from a scaled aggregate figure produces a meaningless result — confirmed exactly against the live trade's real numbers (`19.45 − 22.40 = −2.95`, matching the bug precisely).

**Scope, deliberately narrow:** exit *decisions* (`shouldExitIronCondor()`/`shouldExitSpread()`) were confirmed unaffected — they already used their own correctly-scaled `entryCredit` independently, per the 2026-07-20 multi-lot fix. Only the stored/displayed `currentValue` field was wrong. The default `markToMarket()` path (used only by `EXPIRY_DAY_STRANGLE`) was investigated and confirmed NOT to have the same bug — both `entryCredit` and `fetchCurrentPrices()`'s result are consistently unscaled there (this was itself deliberately, explicitly decided back on 2026-07-17, not an oversight) — but flagged as fragile if that strategy's `max-lots` config is ever raised above 1. **Deliberately not defensively fixed** — an initial proposed defensive fix for that path was reviewed and found to contain a real bug of its own (conflating "current value" with "P&L" in the formula), and the path isn't currently live-broken, so touching untested code without a live bug to justify it was declined in favor of logging the risk.

**Fix:** derive lot count from `trade.getLegs().get(0).getQuantity()` (all legs share quantity, existing convention), scale `entryCredit` by it before the subtraction — same pattern as the 2026-07-20 fix, applied at the two confirmed sites only.

**Verification:** real diff reviewed, `compileJava` clean, full `clean build` (371/371), and **live-verified twice** directly against the real affected trade — first showing the fix hadn't taken effect due to a stale running app instance (same trap hit multiple times this session), then, after a genuine restart, showing `currentValue` correctly matching `entryCredit × lots − unrealizedPnl` to the exact rupee.

**Commit:** `e2dcc23` on `fix/multi-lot-current-value-scaling` (cherry-picked from an initial commit accidentally made on the unrelated Telegram-alert branch, then cleanly separated), merged to `main` via `c31ad9e`.

## Position Sizing — Institutional Comparison and Real Gaps Identified (2026-07-22)

**Context:** A real live Bear Call Spread trade (7 lots, ₹20L capital, 2% risk-per-trade, confidence HIGH via a hardcoded score=80 used for testing) prompted a review of whether the current position-sizing math was working correctly, and how it compares to institutional/prop-desk practice.

**Confirmed: the 7-lot result is mathematically correct, not a bug.** `maxLossPerLot = (100 - 19.45) × 65 = ₹5,235.75`; `lots = floor((2,000,000 × 0.02) / 5,235.75) = 7`. VIX (12.9) is below the 18 threshold, so no VIX-scaling penalty applied. The hardcoded confidence score had zero effect on lot count, because spread strategies never call the confidence-aware sizing overload — confirmed directly in `BearCallSpreadStrategy.java`, which calls only the 2-argument (capital + VIX) `getPositionSize()` overload.

**Institutional-practice comparison, for context (no action taken on most of this):** current fixed-fractional + VIX-overlay sizing is a legitimate, standard methodology, not naive. What differs from institutional practice: Kelly/edge-based sizing (needs real historical win/loss data TradeMesh doesn't have yet — correctly not pursued), continuous volatility-proportional sizing (current VIX check is a single binary threshold, not continuous), portfolio-level VaR/risk budgeting (see gap below — the real, actionable difference), correlation-adjusted sizing across symbols (not yet relevant — BANKNIFTY strategies aren't live), and drawdown-based throttling (no equivalent exists today).

**Two real gaps logged as a result, prioritized:**
1. **Portfolio-level risk-dollar cap** (see Tracked gaps) — highest priority, cheap to implement correctly, no historical data required. Recommended next step once picked up.
2. **Confidence-based sizing for spreads** (see Tracked gaps) — extends an already-built, already-trusted pattern to Bear Call/Bull Put; lower priority than #1.

**Explicitly not recommended right now:** Kelly criterion, full VaR modeling, or correlation-adjusted sizing — all would be built against zero or near-zero real trade data, which risks being worse than the current simple approach, not better. Revisit once a real multi-week trade history exists, same evidence bar already applied to confidence-score band retuning.

No code changed this session — this was an investigation and design-comparison exercise only.

## `feature/position_sizing_vix_lot_multiplier` — full summary (2026-07-09)

**Starting point:** all four strategies traded a hardcoded `max-lots: 1` regardless of account capital, market volatility, or trade quality — explicitly flagged in README's own Phase 3 roadmap as needing capital-based sizing eventually. This branch built that out in three layers, for Iron Condor and (partially) the two spreads.

**Note (2026-07-15): confirmed during design review that this three-layer sizing system had likely never been observably active in production** — `LotSizeService.getPositionSize()`'s final step caps the computed result at `cfg.getMaxLots()`, which was hardcoded to `1` on every strategy until Kuldeep raised it to real values (`max-lots: 30`, `account-capital: 2000000`) on 2026-07-15, separately from the design review implementation work. The sizing math below was genuinely built and unit-tested correctly; it was simply clamped to always output 1 lot in practice until this config change.

### Layer 1 — Capital-based sizing (all three defined-risk strategies: Iron Condor, Bull Put Spread, Bear Call Spread)

Found and fixed a real circular-dependency bug in passing: the existing `maxLoss = (wingWidth - netCredit) × lotSize × lots` formula couldn't be evaluated before `lots` was known, but `lots` was being derived *from* `maxLoss` in the new design. Fixed by separating `maxLossPerLot` (risk of one lot, computable immediately after `netCredit`) from the final `maxLoss` (computed *after* `lots` is determined). Added `LotSizeService.getPositionSize(BigDecimal maxLossPerLot)`: `lots = floor((accountCapital × riskPercent) / maxLossPerLot)`, floored at 1, capped at `cfg.getMaxLots()` (which now serves as a safety ceiling, not the source of truth). New top-level config: `trading.account-capital`, `trading.risk-percent-per-trade`. `ExpiryDayStrategy` explicitly excluded — it's a naked strangle with no `wingWidth`-bounded max loss, needs its own design discussion (see Tracked Gaps).

### Layer 2 — VIX-based sizing (Iron Condor, Bull Put Spread, Bear Call Spread)

New `getPositionSize(maxLossPerLot, currentVix)` overload: VIX>18 scales to 0.5x, VIX≤18 stays full size, floored at 1 lot even after scaling. Required threading `currentVix` as a new parameter into `IronCondorStrategy.selectStrikesAndBuildSignal()` — it was declared in `evaluate()`'s outer lambda but that method is a separate private method with its own scope, discovered only after a real compile error (assumed-in-scope claims should always be verified, not trusted).

**The accompanying integration test (`IronCondorStrategyVixScalingTest`) required five distinct rounds of real debugging** before passing — a good case study in not accepting "should work" reasoning:
1. A wall-clock-dependent hardcoded `latestEntryTime: "15:00"` in the test's mock config caused every test to fail if run after 3 PM (same bug class as two earlier date-hardcoding incidents this session).
2. The mock option chain's uniform flat LTPs produced exactly zero net credit, correctly rejected by the strategy's min-credit gate — invisible until Standard Output logs were actually read.
3. The initial strike range (±500 from spot) was too narrow for the delta-based strike selector to find a valid far-OTM short strike at all.
4. A stale cached HTML test report was mistakenly read as current output, showing an unrelated "3 open positions" message from a different test run — resolved by re-running fresh via `--info` console output instead of trusting the report file.
5. Once real strikes were known (`shortCall=50600, shortPut=49500` via temporary debug logging) and a correct LTP formula was hand-derived, the final failure was a `BigDecimal` scale mismatch in Mockito's exact-match stubbing (`new BigDecimal("10920")` ≠ `10920.0` under `.equals()`) — fixed by matching the literal's scale to what the real code produces.

**Lesson reinforced:** every one of these was found by reading actual Standard Output/debug logs, never by hand-calculation alone.

### Layer 3 — Confidence-based sizing (Iron Condor only)

New `getPositionSize(maxLossPerLot, currentVix, confidenceScore, minScore)` 4-arg overload, composing VIX-scaling and confidence-scaling multiplicatively. Formula: `multiplier = clamp(0.5 + (score - minScore) / (2 × (100 - minScore)), 0.5, 1.0)`.

**Discovered a real, separate architectural gap in the process:** `BullPutSpreadStrategy`/`BearCallSpreadStrategy` have no confidence-scoring mechanism at all — deferred as its own session (later resolved 2026-07-14, see below).

### Principle established: sizing-vs-scoring double-count

VIX was being used **three times simultaneously**: hard entry gate, confidence-score input, and sizing multiplier. **Established principle: a factor may have a hard gate plus at most ONE graded mechanism.** VIX removed from Iron Condor's confidence score (85-point ceiling), `min-score` recalibrated 60→51.

**Final state: 292 tests, BUILD SUCCESSFUL throughout.**
