## Design Review Findings (2026-07-15) — All 10 Resolved, Verified, and Committed

**Context:** Principal Engineer design-coherence review conducted across 5 sections (capital & risk architecture, strategy selection & market-regime logic, paper-to-live transition, failure-mode design, data & state model), per Kuldeep's request for a structured top-to-bottom review of TradeMesh's design before live trading work begins. Conducted against real pasted evidence (source files, grep output, migrations, Liquibase execution logs) — not narrative. This review **superseded and rejected** two Cline-generated documents (`Architecture.md`, `ArchitectureReview.md`) as unreliable review input: the review document contained a fabricated "no unit tests found in codebase" claim (357 tests actually passed on `main` at review start), scored the system 8.2/10 "production-ready" partly on that basis, and gave zero dedicated treatment to the paper-to-live transition despite that being the stated purpose of the exercise. Both documents also independently described `OrderExecutionService` as an active, functioning component; it is confirmed dead code with zero callers.

**Cross-section synthesis (unchanged from original review):** The findings below share one root pattern, found independently in each section — a real, working mechanism exists alongside a second thing that looks like it does the same job but is dead, broken, or was never wired in, and documentation asserted the non-functional one as real. Confirmed a second time during implementation: `RiskManager`'s dead risk-check surface, `StrategySelector`'s dead priority switch, `OrderExecutionService`'s obsolete signal model, and the duplicate token-health monitors all fit this same pattern. This is not carelessness; it's the natural residue of fast, evidence-disciplined feature development without a periodic whole-system coherence pass.

**Process note worth recording:** every finding below went through the same discipline used throughout this project — Cline proposed a plan, the plan was reviewed and frequently challenged before approval (three findings, #5/#9/#7, were substantially revised or reversed after direct challenge before implementation), implementation was verified against real command output pasted by Kuldeep, not accepted on Cline's self-report. ## Live Monitoring Findings (2026-07-17) — First Real Trade Since the Design Review

**Context:** On 2026-07-16 at 12:49:44 IST, `scheduledDailyEntry()` opened a real Iron Condor position on NIFTY50 (trade ID `c5905e56-8615-4394-b24b-998c0ba34dc9`, 4 legs, confidence score 80/100, entry credit 39.65 pts, 2 lots). This is the first entry since `max-lots` was raised from 1 to 30 (2026-07-15), and a candidate for Stage 4c's first trading-day-boundary observation if it survives to Monday. Direct monitoring of this real position over 2026-07-16/17 surfaced two genuine, previously-undiscovered production bugs, both fixed and verified same-day against the live position — not against synthetic test data.

**Positive confirmation, not a bug:** the three-layer position-sizing system (built 2026-07-09, suspected dormant until the `max-lots` fix) worked correctly end-to-end on this real signal. Verified independently: capital-based sizing → 3 lots (`floor((2,000,000 × 0.02) / 10,423)`), VIX-scaled (VIX 12.9, no scaling) → 3 lots, confidence-scaled (score 80, min-score 51, multiplier ≈0.796) → `floor(3 × 0.796) = 2` lots — exactly matching the real trade's `quantity: 2` per leg and `Max Profit: ₹5154.50` (`39.65 × 65 × 2`). First real evidence this system does what it was built to do.

**Bug 1 — RESOLVED: current-value quantity scaling and netting mismatch.** `GET /trading/positions/open` returned `liveUnrealizedPnl` at exactly half the correct `unrealizedPnl` for this 2-lot position. Root cause: `calculateIronCondorCurrentValue()`, `calculateSpreadCurrentValue()`, and `calculateDefaultCurrentValue()` correctly apply signed SELL/BUY netting (fixed 2026-07-08) but never multiplied by `leg.getQuantity()`, unlike their sibling `calculateIronCondorPnl()`/`calculateSpreadPnl()` methods, which do. Invisible for this project's entire history because `max-lots` was always 1 (quantity=1 makes the missing multiplier a no-op) until 2026-07-15.

Fixed in two passes: (1) added `leg.getQuantity()` scaling to all three current-value methods — confirmed used only by the read-only `calculateLiveUnrealizedPnl()` endpoint, zero exit-decision consumers, no gate concern; (2) separately, `fetchCurrentPrices()` — consumed by `markToMarket()`'s default-strategy path and `closeTrade()` — had no signed netting at all (blind LTP summation), fixed to match the established pattern, but **deliberately left unscaled by quantity**: its `currentValue` is compared directly against the still-unscaled `entryCredit` in the STOP_LOSS/TARGET_HIT ratio checks, and scaling only one side would corrupt the actual exit-trigger decision — deferred to the already-logged, properly-scoped future `BigDecimal`/entity-scaling migration.

**A real self-correction during this fix, caught only by live verification, not a green build:** the first pass left `calculateLiveUnrealizedPnl()` subtracting the still-unscaled `entryCredit` against the newly-scaled `currentValue`, producing a *new*, larger mismatch (`liveUnrealizedPnl` showed -53.65 against a correct -14.0). Caught by re-checking the live API response rather than trusting the build, fixed by scaling `entryCredit` by the trade's quantity before that specific subtraction. Final verification: `liveUnrealizedPnl` and `unrealizedPnl` both showed -14.9, `isPnlLive: true`. Commit `0b811e7`.

**Bug 2 — RESOLVED: `/trading/monitor` querying the wrong table with no status filter.** `POST /trading/monitor` reported `totalPositionsMonitored: 0` despite the confirmed real open position. Two layered causes: (1) `TradingController` called `monitorOpenPositions("NIFTY")`/`("BANKNIFTY")` — neither string matches any stored symbol (`"NIFTY50"`/`"NIFTYBANK"`); (2) once that was fixed, the real bug surfaced: `StrategyExecutionLogRepository.findOpenPositionsBySymbol()` was declared returning `Flux<PaperTrade>` despite the repository extending `ReactiveCrudRepository<StrategyExecutionLog, UUID>`. Spring Data's method-name query derivation ignores "OpenPositions" as descriptive text, honoring only "By Symbol" — confirmed via live SQL debug logging that this generated `SELECT strategy_execution_logs.* FROM strategy_execution_logs WHERE symbol = $1`, querying the audit-log table with no status filter at all. Returned 28 "positions" (historical execution-log rows) against 1 real open position.

Confirmed this had been silently harmless in both real call sites, by accident, not design: `monitorOpenPositions()` — every row from the broken query deserialized with a `null` status (no matching column), and `markToMarket()`'s first line (`status != OPEN`) short-circuits on `null`, so no writes ever occurred; `exitAllPositions()` — confirmed zero callers anywhere in the codebase (dead code, same category as `OrderExecutionService`), and even if called, `closeTrade()`'s re-fetch by ID would find nothing, since the broken query's "PaperTrade" objects carried `strategy_execution_logs` IDs, not real `paper_trades` IDs.

Fixed by adding `PaperTradeRepository.findByStatusAndSymbol(TradeStatus, String)` — a real, correctly-scoped query — and rewiring both `monitorOpenPositions()` and `exitAllPositions()` to use it; removed the broken method from `StrategyExecutionLogRepository` entirely rather than leave it as dead code. Verified at three levels: code diff, live API response (`totalPositionsMonitored: 1`, matching reality), and the actual SQL logged (`SELECT paper_trades.* WHERE paper_trades.status = $1 AND paper_trades.symbol = $2`) — not just a coincidentally-correct count. Commit `7cb49ec`.

**Both fixes required Stage 4c override** (touch `markToMarket()`'s call path / consumer), granted and documented per protocol, same as findings #1/#2/#6. Test count unchanged at 344 throughout — none of the affected methods have dedicated test coverage, further confirming the already-logged exit/entry-path test-coverage gap.

**Bug 3 — RESOLVED: Daily Report's fourth manifestation of the same root-cause pattern.** The 3:45 PM Telegram report on 2026-07-16 said "No trades closed today. Market conditions were not favorable for trading." — despite the real Iron Condor having entered that same day at 12:49 PM and remaining open at report time. ## OptionChainService Live-Fallback Refactor (2026-07-20) — Closing the Actual Root Cause Behind Friday's P&L-Corruption Incident

**Context:** Originally scoped as "Option B" — defer a STOP_LOSS/TARGET_HIT close by one cycle if the underlying price data was known to be a fallback, rather than commit to a hardcoded-zero or stale value (the fallback fix already shipped on 2026-07-17). Before implementing Option B, a direct question reframed the whole approach: **why defer or use stale data at all, when a live Kite fetch could be attempted instead?**

**Investigation found the real fix already existed and just needed wiring in.** `OptionChainService.fetchOptionChain(String symbol)` was confirmed to already implement cache-first-with-live-Kite-fallback: try Redis, and on a genuine cache miss, fetch fresh from Kite directly, then re-cache the result with the same key/TTL convention `PaperTradingEngine` reads from. This method already has 8 other real callers across the codebase (`MarketIntelligenceService`, `IvHistoryService`, `MarketMetricsService`, several schedulers/controllers) — well-exercised, trusted infrastructure. **`PaperTradingEngine` never called it** — it bypassed this entirely, reading Redis raw and falling back to a stale value on *any* cache miss, never attempting a live fetch. This was the actual root cause underlying 2026-07-17's `realizedPnl: 0.00` incident, not merely a symptom the earlier fallback fix (Option A) had softened.

**Confirmed no circular dependency risk** before proceeding: the `zerodha.options` package never imports `execution`, and `PaperTradingEngine` already imports `OptionChain` (the data type) from that same package — the dependency direction was already safely one-way.

**Fix:** added `OptionChainService` as a 9th constructor field on `PaperTradingEngine` (appended after the existing 8, preserving positional-argument compatibility). Refactored `calculateIronCondorPnl()`, `calculateSpreadPnl()`, and `fetchCurrentPrices()` to call `optionChainService.fetchOptionChain()` instead of reading Redis directly — per-leg netting loops left byte-for-byte unchanged, only the data-fetching mechanism changed. Each method's existing fallback value is preserved exactly, now triggered only on a genuine `fetchOptionChain()` failure (no token, Kite itself down) rather than any simple cache miss. The two fully-dead `LOT_SIZES.getOrDefault()` lines inside the two P&L methods (confirmed dead earlier the same day) were naturally removed as part of this change, since the block they lived in was replaced.

**Required updating all 8 test files that manually construct `PaperTradingEngine`**, and two real correction rounds, both caught via actual test-failure evidence rather than accepted on a plan summary:
1. `PaperTradingEngineMarkToMarketDecisionTest`'s constructor was initially given `null` for the new dependency, on the reasoning that it "doesn't call the refactored methods" — **wrong**: this file directly tests `markToMarket()`'s default branch, which calls `fetchCurrentPrices()`. Confirmed via a real failing trade returned completely unmutated (fallback silently firing when it shouldn't have). Fixed with a real mock and proper stubs.
2. `PaperTradingEngineCurrentValueTest`'s two pre-existing "successful path" tests (from the earlier Redis-fallback test group) were never updated to stub the new dependency for a success case, confirmed via a real failure (`predicate failed on value: 0.0`, consistent with an unstubbed mock throwing and silently falling back). **Explicitly reconsidered afterward, at Kuldeep's prompt, whether this was truly the best solution — a real, useful design discipline worth recording:** raised whether the lack of single-flight de-duplication (multiple concurrent positions on the same symbol each independently calling Kite on a simultaneous cache miss, e.g. right after a restart) posed a real risk given Kite's API rate limits. **One genuinely new, separate observation surfaced during that reconsideration, worth tracking:** the option-chain cache's TTL (3 minutes) is shorter than `OptionChainSnapshotScheduler`'s refresh interval (5 minutes) — meaning there's a routine ~2-minute window every cycle where the cache is *expected* to be empty before the next scheduled refresh. A cache miss during this window is arguably a normal, regular occurrence, not a rare restart-only edge case. This doesn't change today's fix (the same observation applies whether or not `PaperTradingEngine` calls `fetchOptionChain()`), but is worth a future look at whether the TTL/refresh-interval mismatch was ever a deliberate choice.

## BigDecimal Migration — Phase 1 (2026-07-21) — Entity Fields and Exit-Decision Arithmetic

**Scope:** Converted `PaperTrade.entryCredit/currentValue/realizedPnl/unrealizedPnl` and `TradeLeg.strikePrice/limitPrice` from `Double`/`double` to `BigDecimal`. This is Phase 1 of the migration first properly scoped 2026-07-15 (115 call sites, 13 files estimated at the time). Actual completed scope: **24 files — 10 production, 13 test, 1 new** (`fetchCurrentPrices()`/`extractLTP()` return-type changes and 13 previously-uncounted test files both added real breadth beyond the original estimate).

**Design decisions, made before implementation, held throughout:**
- Full `BigDecimal` arithmetic (`.subtract()`/`.add()`/`.multiply()`/`.compareTo()`) required end-to-end in every exit-decision-relevant path: `calculateIronCondorPnl()`, `calculateSpreadPnl()`, `shouldExitIronCondor()`, `shouldExitSpread()`, both `markToMarket()` paths, and `isLegBreach()` — the last confirmed exit-decision-relevant mid-session (it's Check 2 inside `shouldExitIronCondor()`/`shouldExitSpread()`, sets `exitReason=LEG_BREACH`, triggers a real close; an earlier attempt to classify it as display-only was caught and corrected).
- Approved double-boundary exceptions, explicitly scoped: `calculateLiveUnrealizedPnl()` and the three `calculate*CurrentValue()` methods (`IronCondor`/`Spread`/`Default`) — confirmed to feed only the read-only `GET` position endpoint, zero exit-decision consumers.
- `fetchCurrentPrices()`/`extractLTP()` return types changed `Double`/`double` → `BigDecimal` (not treated as a boundary), since they feed directly into the exit-decision P&L methods above.

**JSON API formatting:** `@JsonFormat(shape = JsonFormat.Shape.NUMBER, pattern = "0.00")` was tried first (per the original 2026-07-15 plan) and confirmed, via live API verification, **not to work reliably on `BigDecimal`** — output still showed raw database column scale (`21.2000`, `24250.0`, `NUMERIC(18,4)`'s native precision) regardless of the annotation. Replaced with a custom `BigDecimalTwoDecimalSerializer` (`com.trademesh.config`, `@JsonSerialize`) that calls `value.setScale(2, RoundingMode.HALF_UP)` before writing as a JSON number — confirmed working via live `curl` against a real trade (`entryCredit: 21.20`, `currentValue: 0.00`, `strikePrice: 24250.00`). Swagger UI's displayed output was found to be unreliable for this verification (shows cached/normalized numeric formatting inconsistent with the raw wire response) — always verify serialization via direct `curl`, not the Swagger UI panel.

**A real regression was found and fixed via the full test suite, invisible to any compile check across the entire migration:** `DailyReportService.sendDailyReportWithCounts()` had two ternaries (`bestTrade != null ? bestTrade.getRealizedPnl() : 0`, same shape for `worstTrade`) where the null-branch fallback was a bare `int` literal `0`, not `BigDecimal.ZERO`. This compiles cleanly — Java's ternary type inference silently resolves a mixed `BigDecimal`/`int` branch pair to a boxed numeric type — but throws `IllegalFormatConversionException: f != java.lang.Integer` at runtime inside `String.format("%.2f", ...)`, and only when the null branch actually fires (the zero-closed-trades report scenario). Caught by `DailyReportServiceCrossDateTest`'s full suite run, not by `compileJava` or `compileTestJava` at any point. Fixed: `.doubleValue()` on the non-null branch, `0.0` (not bare `0`) on the null branch. **Standing lesson for any future `Double`→`BigDecimal` migration: grep specifically for `!= null ? X.getY() : 0`-shaped ternaries with a bare numeric literal — this class of bug will not surface via compilation at all, only at runtime, and only when the fallback branch is actually exercised.**

**Process notes, reinforcing (not new to) this project's standing evidence discipline:**
- This migration required an unusually high number of correction rounds — multiple confidently-wrong "build successful"/"file complete" claims, later disproven by real compiler/build output, including three separate instances where `PaperTrade.entryCredit`/`currentValue`/`unrealizedPnl` were incorrectly claimed to "accept double" (they are `BigDecimal`). - Full verification chain used for every file, and for the migration as a whole: `compileJava` → `compileTestJava` → `clean build` (371/371 tests) → live API `curl` check. No step was skipped in the final sign-off.

## Position Sizing — Institutional Comparison and Real Gaps Identified (2026-07-22)

**Context:** A real live Bear Call Spread trade (7 lots, ₹20L capital, 2% risk-per-trade, confidence HIGH via a hardcoded score=80 used for testing) prompted a review of whether the current position-sizing math was working correctly, and how it compares to institutional/prop-desk practice.

**Confirmed: the 7-lot result is mathematically correct, not a bug.** `maxLossPerLot = (100 - 19.45) × 65 = ₹5,235.75`; `lots = floor((2,000,000 × 0.02) / 5,235.75) = 7`. VIX (12.9) is below the 18 threshold, so no VIX-scaling penalty applied. The hardcoded confidence score had zero effect on lot count, because spread strategies never call the confidence-aware sizing overload — confirmed directly in `BearCallSpreadStrategy.java`, which calls only the 2-argument (capital + VIX) `getPositionSize()` overload.

**Institutional-practice comparison, for context (no action taken on most of this):** current fixed-fractional + VIX-overlay sizing is a legitimate, standard methodology, not naive. What differs from institutional practice: Kelly/edge-based sizing (needs real historical win/loss data TradeMesh doesn't have yet — correctly not pursued), continuous volatility-proportional sizing (current VIX check is a single binary threshold, not continuous), portfolio-level VaR/risk budgeting (see gap below — the real, actionable difference), correlation-adjusted sizing across symbols (not yet relevant — BANKNIFTY strategies aren't live), and drawdown-based throttling (no equivalent exists today).

**Two real gaps logged as a result, prioritized:**
1. **Portfolio-level risk-dollar cap** (see Tracked gaps) — highest priority, cheap to implement correctly, no historical data required. Recommended next step once picked up.
2. **Confidence-based sizing for spreads** (see Tracked gaps) — extends an already-built, already-trusted pattern to Bear Call/Bull Put; lower priority than #1.

**Explicitly not recommended right now:** Kelly criterion, full VaR modeling, or correlation-adjusted sizing — all would be built against zero or near-zero real trade data, which risks being worse than the current simple approach, not better. Revisit once a real multi-week trade history exists, same evidence bar already applied to confidence-score band retuning.

No code changed this session — this was an investigation and design-comparison exercise only.

## `feature/position_sizing_vix_lot_multiplier` — full summary (2026-07-09)

**Starting point:** all four strategies traded a hardcoded `max-lots: 1` regardless of account capital, market volatility, or trade quality — explicitly flagged in README's own Phase 3 roadmap as needing capital-based sizing eventually. This branch built that out in three layers, for Iron Condor and (partially) the two spreads.

**Note (2026-07-15): confirmed during design review that this three-layer sizing system had likely never been observably active in production** — `LotSizeService.getPositionSize()`'s final step caps the computed result at `cfg.getMaxLots()`, which was hardcoded to `1` on every strategy until Kuldeep raised it to real values (`max-lots: 30`, `account-capital: 2000000`) on 2026-07-15, separately from the design review implementation work. The sizing math below was genuinely built and unit-tested correctly; it was simply clamped to always output 1 lot in practice until this config change.

### Layer 1 — Capital-based sizing (all three defined-risk strategies: Iron Condor, Bull Put Spread, Bear Call Spread)

Found and fixed a real circular-dependency bug in passing: the existing `maxLoss = (wingWidth - netCredit) × lotSize × lots` formula couldn't be evaluated before `lots` was known, but `lots` was being derived *from* `maxLoss` in the new design. Fixed by separating `maxLossPerLot` (risk of one lot, computable immediately after `netCredit`) from the final `maxLoss` (computed *after* `lots` is determined). Added `LotSizeService.getPositionSize(BigDecimal maxLossPerLot)`: `lots = floor((accountCapital × riskPercent) / maxLossPerLot)`, floored at 1, capped at `cfg.getMaxLots()` (which now serves as a safety ceiling, not the source of truth). New top-level config: `trading.account-capital`, `trading.risk-percent-per-trade`. `ExpiryDayStrategy` explicitly excluded — it's a naked strangle with no `wingWidth`-bounded max loss, needs its own design discussion (see Tracked Gaps).

### Layer 2 — VIX-based sizing (Iron Condor, Bull Put Spread, Bear Call Spread)

New `getPositionSize(maxLossPerLot, currentVix)` overload: VIX>18 scales to 0.5x, VIX≤18 stays full size, floored at 1 lot even after scaling. Required threading `currentVix` as a new parameter into `IronCondorStrategy.selectStrikesAndBuildSignal()` — it was declared in `evaluate()`'s outer lambda but that method is a separate private method with its own scope, discovered only after a real compile error (assumed-in-scope claims should always be verified, not trusted).

**The accompanying integration test (`IronCondorStrategyVixScalingTest`) required five distinct rounds of real debugging** before passing — a good case study in not accepting "should work" reasoning:
1. A wall-clock-dependent hardcoded `latestEntryTime: "15:00"` in the test's mock config caused every test to fail if run after 3 PM (same bug class as two earlier date-hardcoding incidents this session).
2. The mock option chain's uniform flat LTPs produced exactly zero net credit, correctly rejected by the strategy's min-credit gate — invisible until Standard Output logs were actually read.
3. The initial strike range (±500 from spot) was too narrow for the delta-based strike selector to find a valid far-OTM short strike at all.
4. A stale cached HTML test report was mistakenly read as current output, showing an unrelated "3 open positions" message from a different test run — resolved by re-running fresh via `--info` console output instead of trusting the report file.
5. Once real strikes were known (`shortCall=50600, shortPut=49500` via temporary debug logging) and a correct LTP formula was hand-derived, the final failure was a `BigDecimal` scale mismatch in Mockito's exact-match stubbing (`new BigDecimal("10920")` ≠ `10920.0` under `.equals()`) — fixed by matching the literal's scale to what the real code produces.

**Lesson reinforced:** every one of these was found by reading actual Standard Output/debug logs, never by hand-calculation alone.

### Layer 3 — Confidence-based sizing (Iron Condor only)

New `getPositionSize(maxLossPerLot, currentVix, confidenceScore, minScore)` 4-arg overload, composing VIX-scaling and confidence-scaling multiplicatively. Formula: `multiplier = clamp(0.5 + (score - minScore) / (2 × (100 - minScore)), 0.5, 1.0)`.

**Discovered a real, separate architectural gap in the process:** `BullPutSpreadStrategy`/`BearCallSpreadStrategy` have no confidence-scoring mechanism at all — deferred as its own session (later resolved 2026-07-14, see below).

### Principle established: sizing-vs-scoring double-count

VIX was being used **three times simultaneously**: hard entry gate, confidence-score input, and sizing multiplier. **Established principle: a factor may have a hard gate plus at most ONE graded mechanism.** VIX removed from Iron Condor's confidence score (85-point ceiling), `min-score` recalibrated 60→51.

**Final state: 292 tests, BUILD SUCCESSFUL throughout.**
