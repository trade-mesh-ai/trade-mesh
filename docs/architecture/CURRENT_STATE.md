## Design Review Findings (2026-07-15) — Held, Not Yet Actioned

**Context:** Principal Engineer design-coherence review conducted across 5 sections (capital & risk architecture, strategy selection & market-regime logic, paper-to-live transition, failure-mode design, data & state model), per Kuldeep's request for a structured top-to-bottom review of TradeMesh's design before live trading work begins. Conducted against real pasted evidence (source files, grep output, migrations) — not narrative. This review **superseded and rejected** two Cline-generated documents (`Architecture.md`, `ArchitectureReview.md`) as unreliable review input: the review document contained a fabricated "no unit tests found in codebase" claim (357 tests actually pass on `main`), scored the system 8.2/10 "production-ready" partly on that basis, and gave zero dedicated treatment to the paper-to-live transition despite that being the stated purpose of the exercise. Both documents also independently described `OrderExecutionService` as an active, functioning component; it is confirmed dead code with zero callers.

**Cross-section synthesis:** The five real findings below share one root pattern, found independently in each section — a real, working mechanism exists alongside a second thing that looks like it does the same job but is dead, broken, or was never wired in, and documentation (README, Architecture.md, or the code's own Javadoc) asserted the non-functional one as real. This is not carelessness; it's the natural residue of fast, evidence-disciplined *feature* development without a periodic whole-system coherence pass — which is exactly why this review was worth doing now, before live trading, rather than after. The reactive foundation, read/write separation, entity pattern, and evidence-first engineering culture were all independently re-verified as genuinely sound and need no rework.

### Tier 3 — touches exit-path/scheduler/DB-write logic, falls under Stage 4c gate discipline

1. **Missing concurrency guard on strategy-specific close paths.** `closeIronCondorTrade()` and `closeSpreadTrade()` (`PaperTradingEngine.java`, ~lines 358 and 1035) mutate the in-memory `PaperTrade` directly and save — unlike the generic `closeTrade()`, which explicitly re-fetches from DB first to guard against the 60-second MTM cycle and a scheduled exit (e.g. `dailySafetyNetCheck`) racing to close the same trade simultaneously. Confirmed currently dormant: no `ThreadPoolTaskScheduler` or pool is configured anywhere (`@EnableScheduling` only, no pool-size setting found), so Spring's single-threaded default scheduler executor makes true concurrent races structurally impossible today — this is safe by infrastructure accident, not by design. Becomes a live race the moment anyone adds a thread pool for an unrelated reason (e.g. fixing cron-drift under load). In live trading this becomes duplicate exit-order placement at the broker, on exactly the DTE_EXIT path Stage 4c exists to validate. **Recommended fix:** consolidate all three close paths into one (`closeTrade()` as sole exit writer) rather than patch each independently — same root cause, don't fix the symptom three times.

2. **`TradingScheduler` does not follow the standard token-guard-at-top pattern.** Six other schedulers (`IntelligenceScheduler`, `IvHistoryScheduler`, `MaxPainScheduler`, `OIAnalysisScheduler`, `VixScheduler`, `OptionChainSnapshotScheduler`) all check `tokenTracker.isTokenAvailable()` before proceeding, per `.clinerules`. `TradingScheduler` — the scheduler that actually places trades — relies on the guard existing deeper in the call chain (inside `OptionChainService`/`VixMonitorService`) instead. Not confirmed broken today, but inconsistent with the documented rule on the highest-stakes scheduler in the system.

### Tier 1 — safe anytime, no behavior-critical risk today

3. **`RiskManager` dead code, with a real latent bug inside it.** `isWithinRiskLimits()`, `calculatePositionSize()`, `checkSectorExposure()`, `checkDailyLossLimit()` — plus the state they feed (`dailyPnlMap`, `positionSizeMap`, `recordTrade()`, `resetDailyTracking()`, `getDailyPnl()`, `getPositionSize()`) — confirmed unreferenced anywhere in `TradingOrchestrator` (direct search, zero matches). Independently broken even if it were wired in: `checkDailyLossLimit()` compares raw P&L against the literal config number (e.g. `2.0`) instead of `2.0% × account capital` — the method's own Javadoc claims "enforcement" but the formula never touches capital. `checkSectorExposure()` is an unconditional `return true` no-op. **Recommend deletion, not repair** — this entire surface duplicates and conflicts with the real, tested three-layer sizing system (`LotSizeService.getPositionSize()`).

4. **`StrategySelector.selectByPriority()` is dead architecture, not a working feature.** Structurally can never receive more than one applicable strategy — regime classification (`MarketCondition`) is a mutually-exclusive if/else chain, and each strategy maps to exactly one regime — so the switch/`findFirst()` filters a list that always has size ≤1. "Priority-based selection," in both its own Javadoc and `Architecture.md`, overstates what the code does; there has never been a second candidate to arbitrate between. **Design decision confirmed via evidence-based comparison of alternatives:** one-regime-one-strategy-no-fallback (Option 1) is correct, not a compromise — regime thresholds were derived *from* their target strategy's own entry preconditions (e.g. SIDEWAYS's IVR/PCR bands are literally Iron Condor's own gate), so a failed confidence score on top of regime match is two independent signals agreeing that today isn't good enough, not a gap needing a fallback strategy. Building real multi-candidate arbitration would additionally require a normalized cross-strategy scoring layer that doesn't exist and isn't currently needed (Iron Condor's 4-factor/85-ceiling score and the spreads' 5-factor/100-ceiling score were deliberately built with different weights and even opposite-sign PCR logic). **Recommended replacement:** `applicableStrategies.getFirst()`, with a defensive `log.error()` if size > 1 ever occurs (should be structurally impossible under current config; if it happens, it's a config error to fix, not a scenario to silently arbitrate).

5. **`OrderExecutionService` is dead code (zero callers, confirmed) and lives in the wrong package.** Actually at `com.trademesh.execution.OrderExecutionService`; both `README.md` and `Architecture.md` document it at `com.trademesh.zerodha.orders` and describe it as actively executing orders via Kite. Either delete it or treat it as the literal starting point for the future `ExecutionAdapter` work (see architectural gaps below) — currently it is neither, just inert code a future reader (human or Cline) will reasonably assume is wired in because the Javadoc and both architecture docs say so.

6. **P&L and price fields should be `BigDecimal`, not `Double`.** `PaperTrade.entryCredit/currentValue/realizedPnl/unrealizedPnl` and `TradeLeg.strikePrice/limitPrice` are all `Double`, despite `.clinerules` mandating BigDecimal arithmetic and the `paper_trades` DB columns being `NUMERIC(18,4)` specifically for exact decimal precision. Harmless in paper trading; a real precision risk once live stop-loss/target comparisons (e.g. `currentValue < entryCredit * 0.5`) run against real capital via float comparison. **Recommend converting before live-trading design work begins** — cheap now, expensive to retrofit once `ExecutionAdapter` logic and order placement depend on the current types.

7. **Missing index on `paper_trades.exit_time`.** `findByStatusAndExitTimeBetween()` (added for the Daily Report bug fix) filters on a column with no index — confirmed via migration inspection (only `status`, `symbol`, `strategy_name`, `trade_date`, and a `trade_date+symbol` composite exist). Invisible at current volume; real cost once live trade history accumulates. Separately: no DB-level constraint backs `existsByStrategyNameAndStatus()` (pure application check-then-act) — add a partial unique index (`WHERE status = 'OPEN'`) as defense-in-depth in the same migration, since it's the same category of "safe only because scheduling happens to be single-threaded" latent risk as finding #1.

8. **`LegType` enum drift.** Actual code (`com.trademesh.strategy.enums.LegType`) has only `ENTRY`, `HEDGE`. Both `README.md` and `Architecture.md` document `ENTRY, EXIT, ADJUSTMENT` — fictional, does not exist in code. Separately worth noting, not urgent: `HEDGE` already exists as a real, defined enum value, ahead of the deferred "should `ExpiryDayStrangle` be hedged" design conversation — worth checking whether it's actually referenced anywhere (`grep -rn "LegType.HEDGE" src/main/java`) before that future session starts; if unused, it's a small head start on that decision either way.

9. **Two independently-built, overlapping token-health monitors.** `TokenExpiryWatcher` (every 5 min, continuous, direct Redis read) and `TokenRefreshScheduler` (8:00 AM health check + 9:00 AM pre-market check, via `authService.isTokenValid()`) do overlapping jobs on different cadences through different mechanisms — both alert via Telegram independently. Neither is individually wrong; worth consolidating into one component with staged severity rather than maintaining two that could drift out of sync in alert wording. `TokenRefreshScheduler` is also misnamed — it detects and alerts only, it does not refresh (Kite Connect has no silent-refresh capability; this correctly matches the accepted "manual token refresh ~6 AM" operational reality documented below — just badly named for what it does).

10. **`@EnableScheduling` declared twice** — correctly on `TradeMeshApplication`, redundantly again on `VixScheduler` (line 23). Harmless; remove the duplicate.

### Architectural gaps — logged for roadmap, not urgent, not blocking Stage 4c

- **No system-wide capital-at-risk budget.** The only real cross-strategy check is the DB-backed concurrent-position cap (max 3, via `RiskManager.isWithinConcurrentPositionLimit()`, confirmed live-wired and sound — queries `paperTradeRepository` directly rather than relying on cached/in-memory state). No aggregation of total capital exposed across simultaneously open positions exists beyond that count. If a real daily-loss circuit breaker is ever built (see finding #3), it should follow the same DB-backed pattern — query realized P&L directly — and be computed as a true percentage of `trading.account-capital` (already exists in config from the position-sizing work), not resurrect the broken in-memory version that should be deleted.
- **Zero broker/execution abstraction exists anywhere in the codebase.** The "shared signal/evaluation layer feeding two distinct execution adapters behind one interface" design (flag-toggle explicitly rejected on architectural grounds) is a stated decision, not code — confirmed via empty search for any adapter/interface pattern. Diagnostic pass found: entry is a clean single chokepoint (`PaperTradingEngine.executeTrade()`, one caller); exit is fractured across three implementations with inconsistent safety guards (see finding #1). **Recommended build order when live design work starts:** (1) consolidate the three close paths per finding #1, (2) extend the state model per the next bullet, (3) only then design `ExecutionAdapter`, scoped narrowly to the two real chokepoints that exist today (`placeEntry`, `placeExit`) rather than a speculative broker-agnostic surface built for capabilities not yet specified.
- **`TradeStatus` has no partial-fill/pending states** (`OPEN`/`CLOSED`/`CANCELLED` only), and `TradeLeg` has no per-leg identity, order reference, or fill-tracking — it's a write-once JSONB blob captured at entry. Both assume instantaneous, guaranteed fills, true by construction in paper trading, false by market reality in live trading. This is the concrete, code-confirmed version of the `PaperTrade`-shape question raised when this review was first scoped. Needs to be extended *before* `ExecutionAdapter` is designed, since the interface's return/state shape depends on it.

## `feature/position_sizing_vix_lot_multiplier` — full summary (2026-07-09)

**Starting point:** all four strategies traded a hardcoded `max-lots: 1` regardless of account capital, market volatility, or trade quality — explicitly flagged in README's own Phase 3 roadmap as needing capital-based sizing eventually. This branch built that out in three layers, for Iron Condor and (partially) the two spreads.

### Layer 1 — Capital-based sizing (all three defined-risk strategies: Iron Condor, Bull Put Spread, Bear Call Spread)

Found and fixed a real circular-dependency bug in passing: the existing `maxLoss = (wingWidth - netCredit) × lotSize × lots` formula couldn't be evaluated before `lots` was known, but `lots` was being derived *from* `maxLoss` in the new design. Fixed by separating `maxLossPerLot` (risk of one lot, computable immediately after `netCredit`) from the final `maxLoss` (computed *after* `lots` is determined). Added `LotSizeService.getPositionSize(BigDecimal maxLossPerLot)`: `lots = floor((accountCapital × riskPercent) / maxLossPerLot)`, floored at 1, capped at `cfg.getMaxLots()` (which now serves as a safety ceiling, not the source of truth). New top-level config: `trading.account-capital`, `trading.risk-percent-per-trade` (placeholder values — need real numbers from Kuldeep before this is meaningful). `ExpiryDayStrategy` explicitly excluded — it's a naked strangle with no `wingWidth`-bounded max loss, needs its own design discussion (see Tracked Gaps).

### Layer 2 — VIX-based sizing (Iron Condor, Bull Put Spread, Bear Call Spread)

New `getPositionSize(maxLossPerLot, currentVix)` overload: VIX>18 scales to 0.5x, VIX≤18 stays full size, floored at 1 lot even after scaling. Required threading `currentVix` as a new parameter into `IronCondorStrategy.selectStrikesAndBuildSignal()` — it was declared in `evaluate()`'s outer lambda but that method is a separate private method with its own scope, discovered only after a real compile error (assumed-in-scope claims should always be verified, not trusted).

**The accompanying integration test (`IronCondorStrategyVixScalingTest`) required five distinct rounds of real debugging** before passing — a good case study in not accepting "should work" reasoning:
1. A wall-clock-dependent hardcoded `latestEntryTime: "15:00"` in the test's mock config caused every test to fail if run after 3 PM (same bug class as two earlier date-hardcoding incidents this session).
2. The mock option chain's uniform flat LTPs produced exactly zero net credit, correctly rejected by the strategy's min-credit gate — invisible until Standard Output logs were actually read.
3. The initial strike range (±500 from spot) was too narrow for the delta-based strike selector to find a valid far-OTM short strike at all.
4. A stale cached HTML test report was mistakenly read as current output, showing an unrelated "3 open positions" message from a different test run — resolved by re-running fresh via `--info` console output instead of trusting the report file.
5. Once real strikes were known (`shortCall=50600, shortPut=49500` via temporary debug logging) and a correct LTP formula was hand-derived, the final failure was a `BigDecimal` scale mismatch in Mockito's exact-match stubbing (`new BigDecimal("10920")` ≠ `10920.0` under `.equals()`) — fixed by matching the literal's scale to what the real code produces.

**Lesson reinforced:** every one of these was found by reading actual Standard Output/debug logs, never by hand-calculation alone — hand-calculated "should be X" values were wrong or unverifiable at least three separate times in this one test's history.

### Layer 3 — Confidence-based sizing (Iron Condor only)

New `getPositionSize(maxLossPerLot, currentVix, confidenceScore, minScore)` 4-arg overload, composing VIX-scaling and confidence-scaling multiplicatively. Formula: `multiplier = clamp(0.5 + (score - minScore) / (2 × (100 - minScore)), 0.5, 1.0)` — continuous, not stepped, and scales relative to whatever `min-score` is actually configured rather than a hardcoded 60.

**Discovered a real, separate architectural gap in the process:** `BullPutSpreadStrategy`/`BearCallSpreadStrategy` have no confidence-scoring mechanism at all (hardcoded `Confidence.MEDIUM` label, no computed score, no `min-score` gate) — confirmed this should exist for them too (the "not every valid setup is equally good" rationale is structure-agnostic), but building it requires real design work, not a copy of Iron Condor's formula: IVR/IV-HV transfer unchanged, ATR% likely needs a different threshold (one-sided vs two-sided breach risk), PCR's interpretation needs to flip from "penalize extremity" to "reward directional agreement," and a new trend-strength factor is likely needed since Iron Condor has no equivalent. Deliberately deferred as its own dedicated session (see Tracked Gaps).

### Principle established: sizing-vs-scoring double-count

While building Layer 3, identified that VIX was being used **three times simultaneously**: hard entry gate (`max-vix`), a confidence-score input (max 15/100 points), and now a sizing multiplier — with the compounding effect between the scoring and sizing treatments never deliberately chosen, just an artifact of building two features independently. **Established principle: a factor may have a hard gate plus at most ONE graded mechanism (confidence-score input OR sizing multiplier, not both).** Acted on it immediately: removed VIX from Iron Condor's confidence score entirely (was max 15 of 100; remaining IVR+IV/HV+ATR%+PCR = max 85), recalibrated `min-score` from 60 to 51 (preserving the 60% pass bar against the new ceiling, Option B — no reweighting of the other four factors' existing point values). Cleaned up a resulting dead `vixData` parameter on `calculateConfidenceScore()` as a byproduct. Added dedicated `IronCondorConfidenceScoreTest.java` — this specific method had zero direct unit test coverage before, only incidental values from unrelated integration tests. **Standing reminder logged for future work: when an ATR%-based sizing multiplier is eventually added, remove ATR% from the confidence score in the same change, following this identical pattern** — don't let it become a second unprincipled double-count.

## P&L netting bug and 11 validated code-review gaps (2026-07-08, merged to main)

**Real bug found while observing the live BEAR_CALL_SPREAD position opened via the retry mechanism this morning (entered 10:30 AM via `scheduledEntryRetry()` — confirms the retry-loop fix works correctly in live conditions: exactly one strategy logged, correct pre-flight gating).**

- `GET /trading/positions/open` showed `unrealizedPnl: -3.35` (stored, correct) vs `liveUnrealizedPnl: -86.15` (live-calculated, wrong) for the same open position — a ~25x divergence.
- Root cause: `calculateSpreadCurrentValue()`, `calculateIronCondorCurrentValue()`, and `calculateDefaultCurrentValue()` (all three, same bug pattern) were **unconditionally summing every leg's LTP** regardless of SELL/BUY direction — instead of netting (SELL adds, BUY subtracts), matching the already-correct convention used in `calculateIronCondorPnl()`/`calculateSpreadPnl()`. This inflated `currentValue`, which inflated the derived `liveUnrealizedPnl = entryCredit - currentValue` into a much larger (more negative) number than the correctly-calculated stored P&L.
- **This was live and actively misreporting P&L on the real open position at the time it was found** — not a theoretical bug caught in review.
- Fixed all three methods to use the correct signed-netting logic, verified against `calculateIronCondorPnl()`'s real, working implementation (confirmed via direct code inspection, not assumption, after two rounds of Cline reasoning from first principles instead of checking).
- Added dedicated test coverage (`PaperTradingEngineCurrentValueTest.java`) with concrete buggy-vs-correct value assertions for all three methods; changed their visibility from `private` to package-private to allow direct testing (matches existing `isDteExitDue()` precedent).
- **Confirmed fix works in practice**, not just tests: same position later closed via `TARGET_HIT` at 11.35 pts profit (3h43m hold) — a genuine multi-hour intraday hold, consistent with the DTE/FORCE_CLOSE_EOD fixes from July 6 actually working as intended. A second live position also showed `unrealizedPnl`/`liveUnrealizedPnl` matching exactly (2.4/2.4) after the fix.
- Recurring issue caught again during this fix: the hardcoded test date in `PaperTradingEngineTest.java` had reverted to `LocalDate.of(2026, 7, 6)` — traced to this being a different feature branch than where the earlier fix landed, not a real regression. Fixed again on this branch; underlying lesson (a fix applied on one branch doesn't exist on siblings branched before that commit) logged as a process note, not a code issue.

**Separately, validated and fixed all 11 gaps from an independent July 5 code-review session** (that session's own CURRENT_STATE.md was reviewed, not treated as authoritative, and every item was independently confirmed via grep/code inspection before fixing — several items turned out more subtle or differently-scoped than originally described):

Fixed via `.flatMap(candle -> Mono.justOrEmpty(parseCandle(candle)))`.
2. **`IvHistoryService` idempotency check reordered** — `existsBySymbolAndTradeDate()` now runs before the expensive `calculateAtmIv()` fetch, not after.
3. **`OIAnalysisScheduler` token tracking added** — now calls `trackTokenMissing()` on token-missing errors, matching sibling scheduler pattern (added `SCHEDULER_NAME` constant).
4. **`OIAnalysis.data` dead column dropped** — write-only, zero read callers confirmed via grep; entity field, write call, and DB column (migration 014) all removed.
5. **`MarkToMarketScheduler` token handling added** — deliberately chose per-trade graceful degradation (Option B) over cycle-skip, since this scheduler is the sole writer of exit decisions (DTE_EXIT/LEG_BREACH/STOPLOSS/TARGET all live inside `markToMarket()`); skipping the whole cycle would silently stop all exits from firing. Also fixed a secondary hardcoded-wall-clock-time bug found while writing tests, via extracting `executeMarkToMarket(LocalTime)`.
6. **`VixScheduler.persistVixData()` token guard added** — matching sibling `fetchVixData()`'s existing pattern.
7. **`VixHistory.fromVixData()` timestamp bug fixed** — was stamping `recordedAt` as `Instant.now()` regardless of whether the underlying VIX value came from a fresh fetch or a 5-min-stale cache hit; now correctly uses `VixData.getFetchedAt()`.
8. **Dead `getLotSize()` wrapper removed** from `MaxPainCalculatorService` — duplicated the already-in-use inline call.
9. **`dailySafetyNetCheck()` retimed and gated** — moved from 9:00 AM (before market open, no holiday awareness) to 9:20 AM with an `isMarketOpen()` filter added, matching sibling scheduled methods. Retiming to 9:20 (not 9:15/9:16) was a deliberate choice to avoid racing `MarkToMarketScheduler`'s first ticks at market open.
10. **`MarketCalendarService.isTradingDay()` fail-open bug fixed** — previously silently treated any year missing from `NSE_HOLIDAYS` as entirely trading days (including real holidays); flagged as a must-fix-before-live-go-live item. Flipped to fail-safe (returns `false`, logs ERROR). Verified via `countTradingDays()`'s actual loop logic that this is conservative in both entry and exit directions, never permissive.
11. **`TradingScheduler` double-subscribe pattern removed** — all 4 scheduled methods had wrapped an already-`Mono`-returning call in `Mono.fromRunnable()` then subscribed twice (once inside, once outside); simplified to a single `flatMap` + single `subscribe`, confirmed behavior-identical via unchanged test count.

Each item above was independently re-verified via grep/direct code inspection before fixing — not accepted on the other session's narrative alone, consistent with this session's standing evidence discipline. Several Cline "done" reports during this work were rejected and required rework (missing test coverage on the first pass for at least 4 of the 11 items; a wrong-file mixup on item 8; a fire-and-forget test-timing bug on item 5 traced to hardcoded wall-clock time).

**Cost-control rules established 2026-07-13, apply to all future sessions:**

1. **Two distinct root causes on the same test/method → stop and rethink the whole approach; do not patch a third symptom.** The signal isn't a raw failure count — it's whether the failure *reason* changed between attempts. If a fix reveals a new, unrelated failure (not a continuation of the same root cause), that's one strike. Two such strikes means stop iterating incrementally and rebuild the test/approach from scratch instead. If the same root cause just needs one more clean iteration to fully resolve (e.g. a threshold fix that also needed a missed-import fix), that's not a strike — keep going. This was derived from two real incidents this session: the VIX-scaling integration test (five genuinely distinct root causes, should have triggered a rethink far earlier than it did) and a confidence-score boundary test (repeated impossible hand-calculated point values across multiple assertions in one method — should have triggered a full rebuild after the first impossible value, not incremental patching).
2. **Verify via debug output (not hand-calculation) for: dollar figures, P&L, lot sizes, and any exact test assertion value.** Skip verification for intermediate test-setup values that don't directly drive an assertion, and for config/design values already confirmed via grep earlier in the same session. **Re-verify the moment an already-confirmed design value gets used to hand-derive a new precise assertion number** — a design decision being correct (e.g. the delta-ratio-scaled ATR% bands) does not make a hand-calculated test value using that design correct; those are different levels of confidence and the second one still needs its own verification.
