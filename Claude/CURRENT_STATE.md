## New this session (2026-07-08) — live P&L netting bug + 11 validated code-review gaps, on `feature/issue_in_pnl_calulation`

**Real bug found while observing the live BEAR_CALL_SPREAD position opened via the retry mechanism this morning (entered 10:30 AM via `scheduledEntryRetry()` — confirms the retry-loop fix works correctly in live conditions: exactly one strategy logged, correct pre-flight gating).**

- `GET /trading/positions/open` showed `unrealizedPnl: -3.35` (stored, correct) vs `liveUnrealizedPnl: -86.15` (live-calculated, wrong) for the same open position — a ~25x divergence.
- Root cause: `calculateSpreadCurrentValue()`, `calculateIronCondorCurrentValue()`, and `calculateDefaultCurrentValue()` (all three, same bug pattern) were **unconditionally summing every leg's LTP** regardless of SELL/BUY direction — instead of netting (SELL adds, BUY subtracts), matching the already-correct convention used in `calculateIronCondorPnl()`/`calculateSpreadPnl()`. This inflated `currentValue`, which inflated the derived `liveUnrealizedPnl = entryCredit - currentValue` into a much larger (more negative) number than the correctly-calculated stored P&L.
- **This was live and actively misreporting P&L on the real open position at the time it was found** — not a theoretical bug caught in review.
- Fixed all three methods to use the correct signed-netting logic, verified against `calculateIronCondorPnl()`'s real, working implementation (confirmed via direct code inspection, not assumption, after two rounds of Cline reasoning from first principles instead of checking).
- Added dedicated test coverage (`PaperTradingEngineCurrentValueTest.java`) with concrete buggy-vs-correct value assertions for all three methods; changed their visibility from `private` to package-private to allow direct testing (matches existing `isDteExitDue()` precedent).
- **Confirmed fix works in practice**, not just tests: same position later closed via `TARGET_HIT` at 11.35 pts profit (3h43m hold) — a genuine multi-hour intraday hold, consistent with the DTE/FORCE_CLOSE_EOD fixes from July 6 actually working as intended. A second live position also showed `unrealizedPnl`/`liveUnrealizedPnl` matching exactly (2.4/2.4) after the fix.
- Recurring issue caught again during this fix: the hardcoded test date in `PaperTradingEngineTest.java` had reverted to `LocalDate.of(2026, 7, 6)` — traced to this being a different feature branch than where the earlier fix landed, not a real regression. Fixed again on this branch; underlying lesson (a fix applied on one branch doesn't exist on siblings branched before that commit) logged as a process note, not a code issue.

**Separately, validated and fixed all 11 gaps from an independent July 5 code-review session** (that session's own CURRENT_STATE.md was reviewed, not treated as authoritative, and every item was independently confirmed via grep/code inspection before fixing — several items turned out more subtle or differently-scoped than originally described):

## Tracked gaps (logged, not scheduled)

- No exit path places a real Kite order — all exits remain DB-only. Address only when live trading becomes active.
- Leftover unused mock fields from earlier test-fixing iterations — cosmetic, Tier 1, safe anytime.
- **Strategy names and symbol names are hardcoded as string literals throughout the codebase** (e.g. `"IRON_CONDOR"`, `"BULL_PUT_SPREAD"`, `"NIFTY50"` compared via `.equals()` in `StrategySelector.selectByPriority()`, `PaperTradingEngine.isLegBreach()`, and elsewhere). Identified as real technical debt, not a bug — nothing behaves incorrectly today because of it. Deliberately deferred: introducing a `StrategyName`/`Symbol` enum touches config binding (`application.yml` keys are strings), DB columns (`strategy_name` stored as text), Liquibase migrations, and dozens of call sites — a large, cross-cutting refactor that deserves its own dedicated review pass, not a bolt-on to other work. This exact tradeoff was already considered once before this session (during the `isLegBreach()` LEG_BREACH work) and explicitly rejected as out of scope at the time; still correct to defer.
- **`ExpiryDayStrategy` is not covered by the new capital-based/VIX/confidence position-sizing work.** All three sizing layers (capital-based, VIX-scaled, confidence-scaled) depend on `maxLossPerLot = (wingWidth - netCredit) × lotSize` — a formula that assumes a defined-risk credit spread with a bounded wing width. `ExpiryDayStrategy` is a naked strangle with no `wingWidth` concept and theoretically unlimited risk until a stop-loss triggers, so this formula genuinely doesn't apply. It still uses `strategyConfig().getMaxLots()` directly, unscaled. Needs its own design discussion for how to derive a per-lot risk estimate (likely margin-requirement-based or stop-loss-implied, not wing-width-based) before any sizing logic can be added — deliberately deferred, not overlooked, to avoid scope-creeping the already-complex defined-risk sizing work.
- **`BullPutSpreadStrategy` and `BearCallSpreadStrategy` have no confidence-scoring mechanism at all**, unlike `IronCondorStrategy`. Discovered while scoping confidence-based position sizing: Iron Condor computes a real weighted score (IVR + IV/HV + ATR% + VIX + PCR) and gates entry on a configurable `min-score` threshold; the two spread strategies instead set a hardcoded `Confidence.MEDIUM` label directly on the signal with no computation and no minimum-score gate at all. This means confidence-based sizing currently only applies to Iron Condor — the two spreads were correctly left unchanged in that work, since there's no computed score to scale by. This is a bigger architectural gap than the sizing question alone: two of three defined-risk strategies currently have no mechanism to skip a technically-valid-but-low-quality setup the way Iron Condor does. **Confirmed this should exist for spreads too — the "is this setup good, not just technically valid" rationale is structure-agnostic, not specific to neutral strategies.** But it is NOT a simple copy of Iron Condor's formula, since spreads are directional: IVR and IV/HV are direction-agnostic and transfer unchanged; ATR% likely needs a different threshold (one-sided breach risk vs. Iron Condor's two-sided); PCR's interpretation needs to flip from "penalize extremity" (Iron Condor wants balance) to "reward agreement with trade direction" (a spread wants the market's positioning to confirm its directional bet); and a genuinely new factor — trend strength/momentum in the trade's intended direction — is likely warranted, since Iron Condor has no equivalent (it profits from absence of trend). Deliberately deferred as its own dedicated design session, not scoped alongside the sizing work.
- **Principle established (2026-07-09): a factor must not simultaneously be a component of the confidence score AND an independent sizing multiplier.** Discovered while adding VIX-based sizing: VIX already appeared in Iron Condor's confidence score (max 15 of 100 points) as well as the new hard-coded sizing tier (VIX>18→0.5x) and the pre-existing hard entry gate (`max-vix`) — three overlapping treatments of the same variable, with the compounding severity between the score-based and sizing-based treatments never deliberately chosen, just an accidental artifact of building the two mechanisms independently. **Rule going forward: a hard gate (binary "is this tradeable at all") may coexist with at most ONE graded mechanism (confidence-score input OR sizing multiplier, not both) for the same factor.** When a new sizing multiplier is added for a factor that's already a confidence-score input, remove that factor from the confidence-score formula in the same change, and recalibrate `min-score` proportionally (do not reweight the remaining factors to hit a new arbitrary point total — preserve their existing point values unchanged and adjust only the pass threshold, since this requires zero changes to already-working scoring logic). **Action taken now: VIX removed from Iron Condor's confidence score** (was max 15 of 100 points; remaining IVR+IV/HV+ATR%+PCR = max 85 points unchanged), **`min-score` recalibrated from 60 to 51** (60/100 = 60% pass bar preserved against the new 85-point ceiling: 60% × 85 ≈ 51). **Standing reminder for future work: when an ATR%-based sizing multiplier is added (currently only discussed, not built), remove ATR% from the confidence-score formula in that same change, following this identical pattern** — do not let ATR% become a second instance of the same unprincipled double-count.
